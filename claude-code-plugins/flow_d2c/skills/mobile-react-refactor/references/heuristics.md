# 启发式规则

使用这些规则来稳定移动设备的布局以及后续的 Compose 翻译。优化目标是手机间的一致性，而非任意的桌面扩展。

## 输入质量

最佳基线输入：

- 原始 JSX 或 TSX 组件
- 单屏：一张名为 `Preview.png` 的截图
- 多屏 flow：每个 screen 一张 `Preview-screen-**.png` 截图；不要使用 `Preview.png`

最佳增强输入：

- 原始 JSX 或 TSX 组件
- 单屏：`Preview.png`
- 多屏 flow：`Preview-screen-**.png` 映射
- 审计输出的关键几何数据

为什么这很重要：

- 代码揭示结构、父子关系和显式约束
- 当前参考截图揭示视觉意图、分组、重叠和构图条带

不要仅凭截图判断父子关系。如果当前参考截图可用，不要仅凭代码判断视觉条带位置。单屏参考截图是 `Preview.png`；多屏参考截图必须是当前 screen 对应的 `Preview-screen-**.png`。

在重构 class 之前，编写简短的意图伪代码，命名壳、支撑层、浮动组和重叠归属。这是截图阅读与 JSX 编辑之间的桥梁。

## 分类规则

按顺序使用这些规则。在第一个确信匹配时停止。

### `background`

常见信号：

- `absolute inset-0`
- `bg-[url(...)]`、`bg-cover`、`bg-center`
- 无交互内容

通常可以安全地折叠回父容器背景。

### `support-layer`

常见信号：

- 位于浮动内容下方的实色条带或色块
- 在视觉上支撑下一个重叠的壳
- 常与渐变色块配对
- 非交互性，但不可丢弃

不要过早移除此层。它通常解释了为什么下一个白色内容壳应该重叠特定条带，而非仅仅位于前一个区域下方。

### `overlay`

常见信号：

- 覆盖另一个节点或边缘
- `absolute inset-x-0 bottom-0`
- 渐变遮罩
- 徽章、下划线、卡片底部、浮动工具栏

通常保持为 `absolute`。

提问：

- 它是否覆盖另一个节点？
- 它是否贴边于父级？
- 移除堆叠是否会改变视觉含义？

### `floating-content`

常见信号：

- 在视觉上位于 hero 或媒体区域之上
- 包含普通内容，如头像、标题、元文本
- 使用显式坐标定位，但实际上不是遮罩或控制 chrome

首先将锚点相对于直接父级标准化。然后决定是保持分层还是移入内容容器。

使用当前参考截图回答：

- 它是否实际位于中间视觉条带？
- 它是否与兄弟内容分组？
- 它在视觉上是贴边的，还是仅在数值上接近边缘？

### `flow-content`

常见信号：

- 常规内容块
- 统计、文本组、按钮、区域
- 没有理由重叠另一个元素

转换为正常流。不要保持为 `absolute`。

### `device-chrome`

常见信号：

- 仿状态栏
- 仿 home indicator
- 硬件或 OS 框架模拟

对于面向截图的工作，在像素验证循环期间保留 device chrome，以便捕获的预览和当前参考截图在相同的视觉基线上测量。

仅在以下条件之一为真时删除或省略 device chrome：

- 像素一致性已经足够好，剩余工作是产品清理
- 用户明确不想要设备模拟
- 工作流已进入 Compose 翻译或最终产品清理阶段

## 意图伪代码

在编辑之前编写 5 到 15 行伪代码。保持语义化，而非实现细节化。

好的示例：

```txt
Page
  HeroShell
    BackgroundImage
    HeroSupportLayer
    Toolbar
    UserInfo

  WhiteContentShell
    ProfileStats
    ProfileActions
    Tabs
    WorksGrid
```

伪代码必须回答：

- 哪些节点属于同一个壳
- 哪一层支撑下一个壳的重叠
- 哪些块在一个壳内继续流式排列
- 哪些节点是真正的 overlay，与壳内普通内容的区别

如果你无法用伪代码解释页面，暂不要编辑 class。

## 锚点标准化

仅对 `flow-content` 和 `floating-content` 标准化锚点。

始终相对于直接父容器标准化。除非父级确实是页面，否则不要相对于整个页面标准化。

目标不是"将所有内容重写为 `left/top`"。目标是"识别此节点锚定到什么，然后相对于直接父级表达相同含义"。

转换：

- `right` -> `left = parentWidth - right - width`
- `bottom` -> `top = parentHeight - bottom - height`

仅在保留节点语义锚点时使用这些转换。如果节点确实是右锚定、底锚定或边锚定的，保留该锚点。

不要对以下情况执行此操作：

- 遮罩
- 渐变
- 下划线
- 语义上贴边的 overlay
- 有意右对齐的控件或徽章
- 视觉含义依赖于底部锚定的内容

优先使用以下转换：

- `left + width` -> `left + right`
- `right + width` -> `left + right`
- 固定水平放置 -> `padding(horizontal = ...)`
- 固定卡片尺寸 -> `aspect-ratio`

在转换结构之前，将原始位置语义冻结为父级相对比率。对于 hero 或媒体构图，记录：

- `top / parentHeight`
- `bottom / parentHeight`
- 与下一个区域的重叠深度

当白色内容壳在视觉上重叠前一个壳时，相对于前一个壳边界测量该重叠。不要将内容壳重写为页面级绝对定位，除非其高度和关系确实是固定的。

这防止了一种常见失败模式：

- 原始：内容位于 hero 内的测量条带处
- 错误重构：内容被推到底部，使用 `mt-auto` 或 `justify-end`
- 结果：区域变得"更整洁"但视觉上错误

如果原始节点不是贴边的，不要仅因为更容易表达就将其重写为贴边。
如果原始节点是贴边的，不要仅因为更容易表达就将其重写为 `left/top`。

如果代码和截图不一致，按以下顺序优先：

1. 信任代码中的父子结构
2. 信任当前参考截图中的视觉位置
3. 用审计中的父级相对测量确认

## 区域恢复顺序

使用此顺序以减少回退：

1. 外层页面容器
2. hero 壳
3. 下一个壳下方的支撑层
4. 白色内容壳归属
5. hero 内容
6. 信息面板内部
7. 标签页
8. 重复列表 / 卡片

## 尺寸释放规则

- 在重构内部之前，将顶层固定宽度转换为 `w-full`。
- 在优化内部 overlay 之前，将重复的固定尺寸卡片转换为 `aspect-*` 和 grid。
- 每次只改变一个缩放轴：
  - 先宽度
  - 然后高度 / 宽高比
  - 然后重叠

对于移动端适配：

- 当有意义的顶部偏移表达真实产品意图时保留它们
- 比固定位置更早移除固定宽度
- 用父级相对测量替换全画布测量
- 将安全区域冲突视为布局 bug，而非优化
- 在简化内部布局之前保留 hero 构图条带
- 重建浮动内容时，优先使用父级相对百分比而非猜测的底部锚定
- 当一个区域在视觉上覆盖前一个区域时，优先使用壳重叠语义而非页面坐标定位

## 警告信号

如果出现以下情况，停止并重新评估：

- 移除 `absolute` 改变了堆叠含义
- 移除深色条带或实色底层使下一个壳重叠什么变得不清晰
- hero 内容块突然掉到面板后面
- hero 内容块从测量的顶部条带移动到底部对齐的条带
- 标签页和网格偏离了视觉上拥有它们的壳
- 白色内容区域看起来只是附在 hero 下方，而截图显示有明确的重叠
- overlay 仍然相对于页面而非其父级定位
- 预览资源加载失败且对比度消失
- `w-full` 使组件变窄，因为预览壳是收缩包裹的
