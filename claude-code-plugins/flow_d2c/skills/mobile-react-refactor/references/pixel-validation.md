# 像素验证

当用户要求与截图的像素级一致性，而非仅移动端安全适配时，使用此参考。

## 目标

将截图匹配变为可复现的循环：

1. 从导出中冻结关键几何
2. 在验证壳中渲染重构
3. 以与当前参考截图相同的尺寸截取新截图
4. 将新截图与当前参考截图比较
5. 使用 diff 模式决定哪些几何仍然有误

截图命名约定：

- 单屏 Figma React：当前参考截图是 `Preview.png`。
- 多屏 Figma React flow：当前参考截图必须是对应 screen 的 `Preview-screen-**.png`，例如 `Preview-screen-01.png`。
- 多屏 flow 不要创建、读取或依赖 `Preview.png`；如果某个 screen 缺少 `Preview-screen-**.png`，先停止补齐截图证据。

## 编辑前冻结这些数值

在第一次重构遍历之前，从导出代码记录这些值：

- 根宽度和高度
- hero 高度
- 面板相对于前一个壳的重叠深度
- 工具栏顶部偏移
- 头像尺寸及其相对于 hero 或支撑壳的 top/left 偏移
- 标题/元信息块相对于头像组父级的顶部偏移
- 标签页高度和激活下划线粗细
- 重复卡片宽高比和间距大小

对于面向像素的工作，如果导出已揭示更精确的数值，不要从工具近似值如 `-mt-8` 开始。先将原始数值转换为父级相对比率，然后以响应式方式表达该比率。

如果导出包含仿状态栏、home indicator 或其他在当前参考截图中也可见的 device chrome，在截图匹配期间保留这些层。过早移除它们会改变顶部和底部视觉基线，使像素 diff 产生误导。

## 截图捕获

优先使用 Playwright，因为它使截图捕获可复现。

读取 `config.json` 并使用 `pixelValidation` 中的值。

在第一次捕获之前，检查当前参考截图的尺寸，并将该尺寸视为截图一致性的真实来源。

重要：

- 捕获的截图宽度和高度应与当前参考截图匹配
- 如果 Playwright 设备预设产生不同的截图尺寸，不要仅使用该预设进行 diff
- 当截图尺寸和参考尺寸不同时，先修复视口或捕获尺寸，再判断布局不匹配
- 这避免了因背景裁剪、设备缩放和图像重采样造成的虚假 diff

典型尺寸检查：

```bash
sips -g pixelWidth -g pixelHeight <reference-preview>
```

不要使用 `cat`、`head`、`grep` 或 `sed` 等面向文本的命令检查参考截图或 `current-preview.png`。这些是二进制文件，可能产生无意义输出或工具故障。使用 `sips` 或 `file` 等图像安全命令，然后依赖捕获的截图加上 `scripts/pixel_diff.py` 进行比较。

首选命令：

```bash
python3 scripts/capture_preview.py \
  --react-root react \
  --reference <reference-preview> \
  --output current-preview.png
```

此辅助脚本为 `react/dist` 启动临时预览服务器，绑定唯一的 localhost 端口，从 `config.json` 读取 `waitMs`，并在写入 `current-preview.png` 之前将视口匹配到当前参考截图。

不要将设备预设视为真实来源。在写入 `current-preview.png` 之前，使用辅助脚本或等效的匹配视口或捕获尺寸。

如果多个运行可能并行进行，永远不要假设预览在 `4173` 端口。辅助脚本已通过为当前运行选择实际空闲端口来解决此问题。

如果 Playwright 未安装在 shell 环境中，在第一次捕获之前安装它及其浏览器运行时：

```bash
npm install -D playwright
npx playwright install
```

不要在远程资源完成加载之前从截图中判断像素一致性。使用超时或稳定选择器。

如果 `scripts/pixel_diff.py` 报告缺少 Pillow，先安装它：

```bash
python3 -m pip install Pillow
```

典型 diff 命令：

```bash
python3 scripts/pixel_diff.py <reference-preview> current-preview.png --channel-threshold 96 --diff-out pixel-diff.png
```

## Diff 解读

将当前参考截图与捕获的截图比较，并检查两者：

- 不匹配比率
- diff 图像
- 不匹配集群所在的视觉区域

按以下判断顺序：

1. 检查 diff 图像并识别主要不匹配集群
2. 推断每个集群可能的几何原因
3. 选择下一个要修复的单一集群
4. 仅将不匹配比率作为辅助指标，确认整体方向是否在改善

不要仅将低不匹配比率视为 UI 足够忠实的证明。即使全局比率看起来可接受，单个可见的布局错误仍然重要。
当主要布局几何已经正确时，不要仅为了消除微小的 font-weight、letter-spacing 或个位数间距差异而继续循环。

将 diff 图像用作几何提示：

- 粗水平条带不匹配通常意味着壳高度或重叠深度有误
- 集中在头像/标题附近的不匹配意味着浮动组锚点或尺寸有误
- 所有卡片上的不匹配通常意味着宽高比、裁剪或间距有误
- 大部分背景图上的不匹配可能仅意味着截图尺寸或裁剪与当前参考截图不匹配
- 仅顶部栏的不匹配通常意味着安全区域或工具栏顶部偏移有误
- 顶部或底部边缘的不匹配可能仅意味着 device chrome 被过早移除

不要立即同时调整多个不相关区域。一个集群不匹配应产生一个几何修正。

## 何时停止

对于面向截图的工作，继续直到以下条件为真：

- 主要壳边界对齐
- hero 内容条带与截图条带匹配
- 面板重叠深度在视觉上对齐
- 卡片匹配宽高比和间距
- 不匹配比率足够低，剩余噪声主要是图像裁剪或抗锯齿
- 剩余不匹配可以解释，且不隐藏明显的布局缺陷

数值停止规则：

- 当 `mismatch_ratio < 0.1` 时提前停止，前提是剩余 diff 不隐藏明显的结构性布局错误
- 否则当修复轮次超过 5 时停止，并清楚报告残留不匹配集群

此 skill 不要求零差异图像。它要求一个稳定的、可解释的近似匹配，且剩余不匹配已被理解。如果 diff 仍显示有意义的构图或布局错误，通过 `0.1` 阈值是不够的。
如果剩余不匹配主要是排版细节或微小间距微调，将其视为可接受的停止点并明确报告，而非继续循环。

在像素一致性可接受之后，如果用户想要生产就绪的 UI 而非设备模拟，你可以移除 `device-chrome` 作为清理步骤。
